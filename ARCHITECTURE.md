| **License** | CC-BY-NC-4.0 |
| **Execution** | 100% server-side — no client assets, rendering, or GUI |

### Purpose

In-RP provides a complete **Roleplay (RP)** system for Minecraft servers:

- **RP Toggle** — players enable/disable RP mode, receiving visual markers (nametag, chat, tab list).
- **AFK System** — automatic and manual idle detection, RP auto-exit, tab list/nametag markers, and optional idle kick.
- **Lives System** — death counting with configurable limits; eliminated players enter spectator or get kicked.
- **Dice Rolling** — `/roll` with `NdS` notation and proximity broadcast.
- **Gameplay Rules** — PvP, block break/place restrictions for RP players.
- **Administration** — admin commands with confirmation for bulk actions.

### 2.1 `commands/` — Brigadier Commands

All commands are registered in `InRP.onRegisterCommands` via `RegisterCommandsEvent`.

| Class | Command | Permission | Description |
|:---|:---|:---|:---|
| `RPCommand` | `/rp` | None | Toggle RP, sound feedback |
| `AFKCommand` | `/afk` | None | Toggle AFK status, global broadcast, 3s anti-spam |
| `RollCommand` | `/roll` | None | Dice with proximity broadcast |
| `LivesCommand` | `/lives` | None | Query lives (self or target) |
| `RPAdminCommand` | `/rpadmin` | OP 2+ | Full administration |

`RPAdminCommand` groups subcommands: `set`, `config`, `lives` (set/revive/setdeaths/action/applydefault), `confirm`, and `help`.

### 2.3 `data/` — Persistence

#### Data Attachments (`InRPAttachments`)

NeoForge Data Attachments is the primary player state persistence mechanism. Data is automatically serialized in the player's `.dat` file and **survives death** via `copyOnDeath()`.

| Attachment | Type | Default | Purpose |
|:---|:---|:---|:---|
| `IN_RP` | `Boolean` | `false` | Player is in RP mode |
| `IS_AFK` | `Boolean` | `false` | Player is marked as AFK |
| `DEATH_COUNT` | `Integer` | `0` | Accumulated death counter |
| `MAX_LIVES` | `Integer` | `-1` | Lives limit (-1 = unlimited) |
| `IS_DEAD` | `Boolean` | `false` | Player permanently dead |

#### JSON Store (`InRPLivesManager`)

An auxiliary store (`inrp_dead_players.json` in world folder) that tracks UUIDs of dead players **independently** from attachments. This allows `revive` to work for offline players — by unmarking the UUID in the JSON, the login handler detects the mismatch and restores the player.

**Integrity guarantees**:
- Access via `synchronized(LOCK)` — thread-safe against concurrent command and event access.
- Atomic save via `Files.move()` with `.tmp` file — prevents corruption if the server crashes during write.

### 2.4 `events/` — Listeners

| Class | Events | Responsibility |
|:---|:---|:---|
| `AFKEventHandler` | `ServerTickEvent.Post`, `PlayerTickEvent.Post`, `ServerChatEvent`, `PlayerLoggedIn`, `PlayerLoggedOut` | Inactivity timer (100-tick interval), instant wake-up, optional kick |
| `ChatEventHandler` | `NameFormat` | Appends `[RP]` suffix to RP player names in chat |

### 2.5 `util/` — Utilities

#### `LocalizationHelper`

Server-side translation system. Loads JSONs from `assets/inrp/lang/` and exposes:
- `getRaw(key)` → raw String with `en_us` fallback
- `format(key, args...)` → formatted String via `String.format`
- `getMessage(key, args...)` → `MutableComponent` using `translatableWithFallback`
- `getPrefixedMessage(key, args...)` → Component with `[In-RP]` prefix

**Fallback chain**: active language → `en_us` → literal key.

#### `ConfirmationManager`

Manages pending actions for bulk commands (≥5 targets):
- `ConcurrentHashMap<UUID, PendingAction>` with 10-second TTL
- Admin receives a message with clickable `[CONFIRM]` button that runs `/rpadmin confirm`
- Console commands (no UUID) always execute immediately
- Automatic cleanup of expired entries on each `requestConfirmation`

## 3. Lifecycle and Critical Data Flows

### 3.1 Mod Initialization

```
InRP.<init>                           ← Constructor called by FML
 ├─ InRPAttachments.ATTACHMENT_TYPES.register(modEventBus)
 ├─ modContainer.registerConfig(SERVER, InRPConfig.SPEC)
 ├─ modEventBus.addListener(onConfigLoad)     ← Reloads translations
 └─ NeoForge.EVENT_BUS.register(...)          ← 5 event handlers (including AFKEventHandler)

InRP.onServerStarting                  ← ServerStartingEvent
 ├─ LocalizationHelper.reloadTranslations()
 └─ InRPLivesManager.init(server)     ← Loads inrp_dead_players.json

InRP.onRegisterCommands                ← RegisterCommandsEvent
 └─ Registers /rp, /afk, /roll, /rpadmin, /lives
```

### 3.2 AFK Lifecycle and Wake-Up Flow

```
Inactivity Timer (ServerTickEvent.Post — every 100 ticks / 5s)
 │
 ├─ idleMillis >= kickTimeoutMillis (if > 0)?
 │    └─ YES → player.connection.disconnect(...)
 │
 └─ idleMillis >= afkTimeoutMillis?
      └─ YES && !isAFK(player) →
           ├─ setAFK(player, true)
           ├─ [autoDisableRPOnAFK] → setInRP(player, false)
           └─ updatePlayerScoreboard() + refreshPlayerTabList() [Silent entry]

Voluntary Command: /afk
 │
 ├─ Cooldown check (3s per UUID) → passed?
 ├─ !isAFK → setAFK(true), disable RP if configured, broadcast to all in chat
 └─ isAFK  → setAFK(false), update nametag & tab, action bar message to player

Wake-Up Detection (PlayerTickEvent.Post / ServerChatEvent)
 │
 ├─ [Guard] !isAFK(player) → RETURN (zero overhead)
 └─ [If AFK and recent action detected (<1500ms)] →
      ├─ setAFK(player, false)
      ├─ ScoreboardHandler.updatePlayerScoreboard(player)
      ├─ Action bar message: "You are no longer AFK"
      └─ Sound feedback (UI_BUTTON_CLICK)
```

### 3.3 Death and Lives Flow

```
LivingDeathEvent(player)
 │
 ├─ [Guard] countDeathsOnlyInRP == true && !isInRP(player) → RETURN (skip)
 │
 ├─ incrementDeathCount(player)
 │
 ├─ [If player has no limit] → apply DEFAULT_MAX_LIVES if > 0
 │
 └─ [If deaths >= maxLives]
     ├─ setDead(player, true)
     ├─ InRPLivesManager.markDead(uuid)    ← Persists to JSON
     └─ Broadcast "[Player] has run out of lives..."
```

```
PlayerRespawnEvent / PlayerLoggedInEvent(player)
 │
 ├─ [Login] If JSON says NOT dead but attachment says dead → REVIVED OFFLINE
 │    ├─ setDead(false), setDeathCount(0), setGameMode(SURVIVAL)
 │    └─ RETURN
 │
 └─ handleDeadPlayerState(player)
      ├─ [If dead] → spectator + message OR kick (based on LIVES_ACTION)
      └─ [If alive] → update tab list
```

### 3.4 Bulk Action Confirmation Flow

```
Admin executes: /rpadmin set @a off
 │
 ├─ targets.size() >= CONFIRMATION_THRESHOLD (5)?
 │    ├─ YES → ConfirmationManager.requestConfirmation(...)
 │    │         ├─ Stores PendingAction with Runnable + timestamp
 │    │         └─ Sends yellow message with clickable [CONFIRM]
 │    │
 │    └─ NO → Executes immediately
 │
 ├─ Admin clicks [CONFIRM] or types /rpadmin confirm
 │    ├─ ConfirmationManager.confirm(uuid)
 │    │    ├─ Pending exists and not expired? → Run Runnable → return true
 │    │    └─ Expired/nonexistent → return false
 │    └─ Feedback: "Action confirmed" or "No pending action"
 │
 └─ Console (no UUID) → Always executes immediately (confirmation bypass)
```

### 3.5 Persistence — Where Data Lives

| Data | Mechanism | File | Survives death? | Works offline? |
|:---|:---|:---|:---|:---|
| RP status, AFK, deaths, max lives, is_dead | NeoForge Data Attachment | `<world>/playerdata/<uuid>.dat` | Yes (`copyOnDeath`) | Read/written by NeoForge |
| Dead players list | `InRPLivesManager` JSON | `<world>/inrp_dead_players.json` | N/A | Yes (independent store) |
| Configuration | `ModConfigSpec` | `<world>/serverconfig/inrp-server.toml` | N/A | N/A |

> **Note**: The mod is 100% server-side. There is no client-side attachment sync. The client only receives: chat messages (Components), scoreboard teams, and standard packets (game mode, tab list).

## 4. Invariants and Golden Rules

### 4.1 Backward Compatibility

- **NEVER** rewrite working code to accommodate new features. New features must be **additive** — new methods, new classes, new subcommands.
- When modifying an existing method, make **surgical** edits — change only the minimum necessary.
- New config parameters **MUST** have defaults that preserve prior behavior. Example: `countDeathsOnlyInRP = false` keeps the pre-existing behavior.

### 4.2 No Hardcoded Text

- **ALL** player-facing text **MUST** use localization keys via `LocalizationHelper`.
- Keys must follow the convention: `inrp.<system>.<action>` (e.g., `inrp.admin.lives.set.success`).
- **MANDATORY** to add the key in **both** lang files (`en_us.json` and `pt_br.json`).
- `en_us.json` is the ultimate fallback — if a key is missing in the active language, English is used. If missing in both, the literal key is displayed.

### 4.3 Defensive Programming

- **Null checks**: Every `Player` access in `InRPAttachments` methods checks for `null` before operating.
- **Input validation**: Commands use Brigadier bounds (`IntegerArgumentType.integer(-1, 100000)`). Configs use `defineInRange` or `defineInList` — never `define()` for values with a finite domain.
- **Fallbacks**: `LocalizationHelper.getRaw()` never returns `null` — returns the literal key if all else fails. `LocalizationHelper.format()` catches `Exception` and returns the raw string.
- **No crashes**: I/O errors in `InRPLivesManager` are logged as `LOGGER.error()` and silenced — the server **must never** crash because of this mod.

### 4.4 Thread Safety

- `InRPLivesManager` uses `synchronized(LOCK)` on **all** accesses to `DEAD_PLAYERS`.
- `ConfirmationManager` uses `ConcurrentHashMap` — safe for parallel access from multiple commands.
- `LocalizationHelper` reloads translations synchronously on the server's main thread (config event).

### 4.5 Server-Side Only

- The mod **DOES NOT** register any client-side resources (models, textures, screens, keybindings).
- All client communication is done via vanilla packets: `SystemMessage`, `PlayerInfoUpdatePacket`, `SoundEvent` (notify), scoreboard teams.
- **NEVER** add client-side dependencies or code that runs on `Dist.CLIENT`.

### 4.6 Atomic Saves

- All JSON file writes **MUST** follow the pattern `write-to-temp → Files.move(REPLACE_EXISTING)`.
- **NEVER** write directly to the destination file — a crash during write would corrupt the data.

## 5. Extension Guide for New Features

### 5.1 Adding a New Command

1. **Create the class** in `commands/` following the existing pattern (static `register(CommandDispatcher)` method).
2. **Register** in `InRP.onRegisterCommands`.
3. If the command is **admin** (OP 2+), consider adding it as a subcommand of `/rpadmin` instead of a root command.
4. If the command accepts **multiple targets**, integrate with `ConfirmationManager` using the 5-player threshold.
5. **Add all strings** to both `en_us.json` and `pt_br.json`.
6. If the command has sound feedback, use `player.playNotifySound()` — never broadcast sound.

### 5.2 Adding a New Event Listener

1. **Create the class** in `events/` with `public static void` method annotated with `@SubscribeEvent`.
2. **Register** in `InRP.<init>` via `NeoForge.EVENT_BUS.register(HandlerName.class)`.
3. Always verify the entity is `instanceof ServerPlayer` before operating.
4. If the event can be canceled, cancel **before** any side-effects.

### 5.3 Adding a New Attachment

1. Declare in `InRPAttachments` following the pattern: `ATTACHMENT_TYPES.register(...)` with `Codec`, `.copyOnDeath()`, and a safe default.
2. Create getters/setters with null checks.
3. The attachment will be automatically persisted in the player's `.dat` file by NeoForge.

### 5.4 Adding a New Config Parameter

1. Declare the `public static final` field in `InRPConfig`.
2. Define it in the `static {}` block within the appropriate TOML section (`push`/`pop`).
3. Use `defineInRange`, `defineInList`, or `define` depending on the value domain.
4. The default **MUST** preserve prior behavior (no breaking changes).

### 5.5 Checklist — Definition of Done

Before considering any change complete:

- [ ] **Surgical code** — minimal edits, no rewriting of working code
- [ ] **Localized strings** — all visible messages use keys in both lang files
- [ ] **Backward-compatible config** — new parameters don't alter pre-existing behavior
- [ ] **Null-safe** — new methods check `null` on player inputs
- [ ] **Thread-safe** — shared state access uses proper synchronization
- [ ] **Green build** — `./gradlew compileJava` passes without errors
- [ ] **Edge case tests** — test with 0 players, 1 player, many players, extreme values (-1, 0, max)
- [ ] **Clean diffs** — no unrelated changes, no unnecessary formatting
- [ ] **ARCHITECTURE.md updated** — if the change alters flows, packages, or invariants, update this document
